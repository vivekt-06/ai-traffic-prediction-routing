# AI-Based Traffic Congestion Prediction and Dynamic Route Optimization (Delhi)

B.Tech CSE minor project. FastAPI + scikit-learn/XGBoost backend, custom **Time-Dependent Shortest Path** router,
React + TypeScript + Leaflet dashboard. **Everything shown in the UI is computed by the backend from real data and saved model artifacts.**

> **Read this first: what the data can and cannot support**
> * The dataset (Kaggle *New Delhi Traffic Probe & Analytics 2024*, 24,938 segments, 12–30 Aug 2024, **hourly**) contains **probe counts, not speeds**.
>   Speed and Congestion Index are a *derived, uncalibrated heuristic* (`configs/congestion.json`). They are relative indicators, not measurements.
> * Hourly data ⇒ **15/30-minute forecast horizons are not supported** and are not shown. Departure scenarios +15/+30/+45 min are supported by TDSP
>   (arrival time decides which hourly forecast applies on each road), not by sub-hourly forecasts.
> * No live traffic feed exists. The app **replays** the dataset window; "Now" is the departure time you pick. OpenStreetMap is a basemap, not traffic data.
> * LSTM / GRU / ST-GCN-GRU are **implemented but have never been trained**: no weights for them exist anywhere in this project. The Model Evaluation page reads each model's status from the backend (**Trained · Ready / Untrained / Error**) and shows metrics only for models that really loaded and passed validation. Training commands: see "Training".

Train 12–23 Aug · validation 24–26 Aug · test 27–30 Aug (chronological, never shuffled). Per-segment statistics use the training period only.

|---|---|---|---|---|---|---|---|
| Historical Average | 24.02 | **21.25** | **44.57** | **29.0** | **0.952** | 67.3% | 0 |
| Linear Regression | 31.63 | 27.32 | 55.25 | 54.5 | 0.926 | 58.0% | 0 |
| Random Forest | 25.73 | 25.15 | 52.81 | 36.0 | 0.933 | 61.7% | 80 |
| XGBoost | 24.28 | 25.13 | 52.23 | 38.7 | 0.934 | 61.7% | 7 |

The **Historical Average baseline beats the learned models** (as the original README also found). With 12 training days the weekly/hourly
pattern dominates; claiming otherwise would be dishonest. Routing uses the model with the lowest *validation* MAE (currently Historical Average); any trained model can be selected in the UI.
MAPE excludes zero targets (reported coverage in the UI). Numbers are regenerated by `scripts/train_model.py` into `models/trained/metrics.json`.

## Quick start
```bash
python -m venv .venv && source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python scripts/init_db.py                                 # SQLite: events + caches
# Artifacts are included in the zip. To rebuild them:
python scripts/build_panel.py                             # features.parquet -> panel.npz (seconds)
python scripts/train_model.py                             # HA, LR, RF, XGBoost (~3 min on 1 CPU)
python scripts/dataset_status.py                          # data-quality statistics -> JSON
pytest -q                                                 # tests

uvicorn api.main:app --port 8000                          # API (+ built UI if frontend/dist exists)
cd frontend && npm install && npm run build               # once; then open http://localhost:8000
# development with hot reload:  npm run dev   -> http://localhost:5173 (proxies /api to :8000)
```
Models are loaded from `models/trained/`; **nothing retrains at startup**. Startup takes ~5–10 s (loads the panel and builds the graph).

## Model status (what "Trained · Ready" means)
The backend decides (`src/model_status.py`, run once at startup, re-run with `GET /api/models?refresh=true`):
* **Trained · Ready**: weights exist **and load**, and a held-out validation prediction passes (finite, non-negative, right shape, not constant). Tree/linear models must also beat a constant predictor on a real held-out hour; Historical Average and the deep models must reproduce their stored **test MAE** from the saved predictions, so `metrics.json` and the weights can never silently disagree. Deep models additionally need `<name>.pt`, `deep_config_<name>.json`, a matching panel fingerprint and, if PyTorch is installed, a `state_dict` whose tensor shapes match the config.
* **Untrained**: no weights/metrics exist (nothing was ever trained). A `--smoke` run does not count (it writes to `models/trained/_smoke/` only).
* **Error**: weights or metrics exist but loading / inference / validation failed. The reason is shown in the UI and in `GET /api/models`; the model is excluded from forecast and routing (HTTP 422 with the reason). A model that fails *during* inference is demoted to Error at runtime.
`python scripts/check_models.py` prints the same report in the terminal.

## Training
All commands run from the project root. Every random choice is seeded (`--seed`, default 42); the chronological split comes from `configs/dataset.json`.
```bash
# 1. Classical models (CPU, ~3 min): Historical Average, Linear Regression, Random Forest, XGBoost
python scripts/build_panel.py          # only if data/processed/panel.npz is missing (needs features.parquet)
python scripts/train_model.py
# 2. Deep models (PyTorch; GPU strongly recommended, e.g. Google Colab T4)
pip install -r requirements-deep.txt   # then install the right torch build from https://pytorch.org
python scripts/train_deep.py --smoke                                   # ~1 min pipeline check; writes ONLY to models/trained/_smoke/
python scripts/train_deep.py --models lstm gru st_gcn_gru --epochs 30  # real training
python scripts/check_models.py                                          # verify readiness
```
Colab: upload the project (including `data/processed/` and `models/trained/`), choose a GPU runtime, run the lines above with `!`, then download `models/trained/` back and restart the API.
**Artifacts** (all in `models/trained/`): `random_forest.joblib`, `xgboost.json`, `linear_regression.joblib`, `historical_average.npy`, `segment_stats.parquet` (train-only per-segment statistics = the preprocessing objects), `metrics.json` (val+test metrics computed from real held-out predictions), and per deep model `<name>.pt`, `deep_config_<name>.json` (architecture, hyper-parameters, preprocessing constants, per-epoch training curve, exact command line, panel fingerprint) and `deep_pred_<name>.npy`.
Deep models are served from the saved prediction matrix (the app replays the dataset window, so no PyTorch is needed at serve time).
**Status of `train_deep.py`: it has NOT been executed by the author's tooling** (the sandbox had no PyTorch, GPU or network). It was reviewed line by line against the data layout and hardened, but expect to fix shape/memory problems on the first GPU run (ST-GCN-GRU is the most memory-hungry; lower `--hidden` first). Do not report deep-model results until `check_models.py` says Ready and `metrics.json` contains your run.
Weather-aware variants (`random_forest_weather`, `xgboost_weather`): `python scripts/fetch_weather_history.py` (internet) then `python scripts/train_model.py --with-weather`.

## Map
* **Library / tiles**: Leaflet 1.9 (used directly, no `react-leaflet` dependency) + **OpenStreetMap standard tiles**, no API key. Attribution is always shown. Provider is configurable: `frontend/.env` → `VITE_TILE_URL`, `VITE_TILE_ATTRIBUTION` (see `frontend/.env.example`). Heavy use needs a provider you are entitled to use ([OSM tile policy](https://operations.osmfoundation.org/policies/tiles/)). OSM tiles are a basemap only: they contain **no traffic and no routing data**.
* **Roads and routes** are the dataset's own segment geometry (real lat/lon); routing is the project's TDSP on that graph, so no external routing service or key is needed. Routes are bidirectional (the dataset has no one-way flag).
* **Predicted vs observed**: the Dashboard/Routes map has a *Predicted | Observed* switch. Predicted = the selected model's forecast; Observed = the same congestion heuristic applied to the observed historical probe counts of that hour. Both are a **replay of Aug 2024 data, not live traffic**, and the map says so. Colours: green Low, yellow Moderate, orange High, red Severe (legend on the card). Click a road for a popup.
* **Why the map looked broken before** (small tile square, no roads): Leaflet's stylesheet was `@import`ed after the `@tailwind` directives, which CSS ignores, so it never reached the bundle. It is now imported in `src/main.tsx`. **Rebuild the frontend** (`npm run build`); the old `frontend/dist` was built with the bug and is not shipped.

## Design notes
* **Features** (shared by training and inference, `src/feature_engineering.py`): hour, weekday, weekend, peak flag, road attributes, value 24 h earlier, mean of hours t-24…t-26, per-segment *train-only* mean. All inputs ≥24 h old ⇒ no target leakage.
* **Congestion Index**: `intensity = clip(pred/P90_train, 0, cap)`, `speed = max(limit·(1−k·intensity), min)`, `CI = 1 − speed/limit`, thresholds in `configs/congestion.json`. One set of arrays feeds map colours, charts and routing.
* **TDSP** (`src/tdsp.py`): earliest-arrival Dijkstra whose edge cost integrates the forecast across hourly buckets by *entry time* (FIFO). Tested against brute force and a hand-computed boundary case. The shortest-distance route is driven through the same forecast for a fair comparison.
* **Road graph**: built from the dataset's own segment geometry (real Delhi roads). OSMnx was not used: observations are keyed to these segments and would need map matching the data can't support. Segments are bidirectional (no one-way attribute); 3 connected components, origin/destination snap to the main one (≤1.5 km).
* **Weather**: Open-Meteo, cached in SQLite, graceful on failure. Context only: deployed models don't use weather. **Events**: `data/contextual/events.csv` (3 events from the dataset README); radii are assumptions; flagged `needs_team_verification`. Events are reported when they overlap a route in space and time but do **not** alter speeds.
* **Map tiles**: OpenStreetMap standard tiles with attribution, shown dark via CSS filter. Respect the [tile usage policy](https://operations.osmfoundation.org/policies/tiles/) (fine for demos; set `VITE_TILE_URL` for heavier use).
